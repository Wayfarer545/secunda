# Сервис процессинга платежей

Асинхронный микросервис приёма платежей: API принимает запрос, обработка идёт в фоне
через эмуляцию платёжного шлюза, результат уходит клиенту webhook-уведомлением.

Стек: FastAPI, Pydantic v2, SQLAlchemy 2.0 (async), PostgreSQL, RabbitMQ (FastStream),
Alembic, dishka (DI), loguru. Пакетный менеджер uv.

## Архитектура

Три процесса из одной кодовой базы:

- **api** - принимает платежи и отдаёт их состояние. С брокером не работает вообще:
  в одной транзакции пишет платёж и событие в таблицу `outbox` (transactional outbox).
- **relay** - выгребает неопубликованные события из `outbox` батчами под
  `FOR UPDATE SKIP LOCKED` и публикует в RabbitMQ с publisher confirms. Упал после
  публикации, но до отметки `published_at` - событие уйдёт повторно, консьюмер это переживёт.
- **consumer** - единственный обработчик: эмулирует шлюз (2-5 с, 90% успех),
  обновляет статус, шлёт вебхук. Идемпотентен к повторной доставке.

### Retry и DLQ

Повторы построены на TTL + dead-letter exchange, без плагинов и таймеров в коде.
При инфраструктурном сбое консьюмер переотправляет событие в retry-очередь с TTL
(2 с, затем 4 с) и счётчиком `x-attempt` в заголовке. Когда TTL истекает, брокер сам
возвращает сообщение в рабочую очередь. После третьей неудачной попытки событие
уходит в `payments.dlq` с заголовком `x-last-error`. У рабочей очереди тоже настроен
DLX: сообщение, которое нельзя даже разобрать, попадает в DLQ, а не теряется.

### Идемпотентность

- **API**: уникальный индекс по `idempotency_key`. Повтор запроса с тем же ключом
  возвращает исходный платёж с тем же `202`. Совпадение тела не проверяется, ключ решает.
- **Consumer**: статус коммитится до отправки вебхука. При повторной доставке платёж
  уже в терминальном статусе, шлюз не вызывается повторно, доигрывается только вебхук.
  Отметка `webhook_delivered_at` защищает от лишних отправок. Доставка "at-least-once":
  получателю вебхуков нужна дедупликация по `payment_id`.

### Принятые решения по ТЗ

- 10% "ошибок" шлюза - это бизнес-исход (`status=failed` + вебхук), а не сбой.
  Retry срабатывает только на инфраструктурные проблемы: недоступный webhook_url,
  ошибки БД, неожиданные исключения.
- "3 попытки" - три полных прохода обработки: первый + два повтора с задержками 2 и 4 с.
- Relay вынесен в отдельный процесс: он должен переживать падения API и не мешать
  его горизонтальному масштабированию.

## Запуск

```bash
docker compose up -d --build
```

Поднимутся postgres, rabbitmq, одноразовый прогон миграций, api (порт 8000),
consumer и relay. `.env` не обязателен: стек стартует с dev-значениями по умолчанию.

- Swagger: http://localhost:8000/docs
- RabbitMQ: http://localhost:15672 (guest/guest)

### Примеры запросов

Создание платежа (заголовки `X-API-Key` и `Idempotency-Key` обязательны):

```bash
curl -X POST http://localhost:8000/api/v1/payments \
  -H "X-API-Key: dev-api-key" \
  -H "Idempotency-Key: order-42" \
  -H "Content-Type: application/json" \
  -d '{
    "amount": "199.90",
    "currency": "RUB",
    "description": "Заказ 42",
    "metadata": {"order_id": 42},
    "webhook_url": "https://example.com/hook"
  }'
```

Ответ `202 Accepted`:

```json
{"payment_id": "f76d6692-...", "status": "pending", "created_at": "2026-08-27T05:04:56Z"}
```

Повтор с тем же `Idempotency-Key` вернёт тот же `payment_id`. Через 2-5 секунд
платёж перейдёт в `succeeded` или `failed`, на `webhook_url` придёт POST:

```json
{"payment_id": "...", "status": "succeeded", "amount": "199.90", "currency": "RUB",
 "processed_at": "...", "metadata": {"order_id": 42}}
```

Состояние платежа:

```bash
curl http://localhost:8000/api/v1/payments/<payment_id> -H "X-API-Key: dev-api-key"
```

Без ключа 401, без `Idempotency-Key` 422, неизвестный id 404.
